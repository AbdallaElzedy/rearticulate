## 1. Baseline and supersede chain

Each model page is written as a delta on a named baseline. The chain below decides what a profile inherits and what its own page overrides. [BP-003, BP-013, BP-025]

| Profile | Baseline | Page basis (verbatim) | Own-page topics that supersede the baseline |
|---|---|---|---|
| fable-5-1 | fable-5 | "Your existing Claude Fable 5 prompts should perform well on Claude Fable 5.1 without changes" (F51-04) | progress updates, finishing the task, scope of changes and tests, edits, formatting, search triggering, batching, history, writing density, quoting sources, long outputs, subagents, vision, safeguards |
| fable-5 | none (guide only) | differences from Opus 4.8 "may require prompt or scaffolding updates" and are "a good prompt to re-evaluate which instructions, tools, and guardrails are still needed" (F5-07); Opus 4.8 rules are not inherited | every section of the page |
| opus-5-5 | opus-5 | "Existing Claude Opus 5 prompts should perform well without changes, and the patterns in Prompting Claude Opus 5 remain a reasonable starting point." (O55-04) | effort calibration, prompts written for thinking disabled, unattended agentic runs, safeguard refusals, progress updates, multi-app exploration, time signals, chat thinking instructions, pasted text, visual inputs, frontend defaults |
| opus-5 | opus-4-8 | "It performs well out of the box on existing Claude Opus 4.8 prompts." (O5-05) | verification, subagents, verbosity, narration, self-correction, deliverable length, thinking-disabled artifacts |
| sonnet-5-5 | sonnet-5 | "Existing Claude Sonnet 5 prompts should perform well without changes, and the patterns in Prompting Claude Sonnet 5 remain a reasonable starting point." (S55-04) | effort calibration, initiative and scope, running without up-front thinking, JSON output on reasoning tasks, progress updates, tool use in chat, mid-turn user messages, coding verification, tolerant tool calls, visual inputs, safeguard refusals |
| sonnet-5 | the Sonnet 4.6 facts printed on its own page | "It performs well out of the box on existing Claude Sonnet 4.6 prompts." (S5-04) | every section of the page; Sonnet 4.6 itself is a legacy-4x model |
| opus-4-8 | opus-4-7 (legacy-4x) | "It performs well out of the box on existing Claude Opus 4.7 prompts." (O48-04) | every section of the page |
| legacy-4x | none (guide only) | the guide's inline mentions and its Migration considerations (BP-002, BP-005) | not applicable |

Rules of the chain:

- A section on the target's own page supersedes the same-topic section of its baseline. Fable 5.1 therefore inherits the f5_* snippets except where a 5.1 section covers the same topic (progress updates, finishing the task, scope of changes and tests, edits, formatting); Opus 5 inherits the Opus 4.8 review coverage, frontend, literalism, and effort-sweep advice except where an O5 section overrides (verification, subagents, verbosity, narration, self-correction).
- A rule the target's page states without a snippet may borrow the baseline's or a sibling's snippet. The Target model item in the Reading line then records "text measured on <page>". Example: O5-12 ("report everything and filter in a separate pass") has no Opus 5 snippet; the borrowed text is o48_review_coverage, recorded as measured on the Opus 4.8 page.
- Each profile file states its baseline in section 1 as "Baseline: <profile or none>; page basis: <quoted sentence>".
- Conflicts between pages are resolved in favour of the target's own page. Two known ones: progress updates (the 5.1 page asks for more narration, the Fable 5 page asks for an outcome-first brief final message) and verification (the Fable 5 page recommends fresh-context verifier subagents at an interval, F5-68; the Opus 5 page says do not use subagents to verify, O5-51).

## 3. Alias table for `--model` (case-insensitive; also matched inside free text)

Matching is case-insensitive and punctuation-insensitive: lowercase the name and treat a dot, a space, a hyphen, and the absence of a separator as equivalent, so "Claude Opus 4.6", "opus-4.6", "opus-4-6", and "opus46" all match the same row. Strip a trailing context-window or variant suffix before matching ("(1M context)", "[1m]", a date stamp), so "Opus 5 (1M context)" and `claude-opus-5[1m]` both resolve to `opus-5`. Suffix stripping covers context-window and date suffixes only, never a point-release digit: ".1" is a version, not a suffix.

Match the longest alias that fits. Normalise the candidate, then test aliases in descending length and take the first that matches, so a name normalising to `fable51` or `mythos51` resolves to `fable-5-1` and never to the shorter `fable-5` alias it contains; the same rule protects any future point-release row. A version number is matched whole: `fable-5` matches only when no further version digit follows, and the same for `mythos-5`, `opus-4-5`, and `sonnet-4-5`. The four collision pairs this settles are fable-5 against fable-5-1, mythos-5 against mythos-5-1, and their `claude-*` forms.

A bare family word with no version resolves in two branches, and either way the inference is recorded in the Reading line. When the family has exactly one model in the guide's thirteen, it resolves to that model: "our Haiku bot" is Haiku 4.5. When the family has several members in the thirteen, it resolves to the newest of them: Opus to Opus 5.5, Sonnet to Sonnet 5.5, Fable to Fable 5.1, Mythos to Mythos 5.1, which routes to `fable-5-1`. The Reading line then reads `Target model: <profile> (bare family name "<word>", assumed newest in the guide's thirteen)` and the `Assumed:` line repeats it. A bare family word is never treated as unrecognised and never falls through to legacy-4x tier B.

## 4. Executing model versus target model

Two model dimensions are kept apart on every run.

- Executing model: the model running the skill inside Claude Code. It governs how the skill itself behaves in Steps 5 to 7 (narration cadence, whether a verification pass runs, how readily it delegates, how it formats, edit style, search before answering at low effort, progress grounding). Resolve it from the system prompt's model identity statement ("You are powered by the model named ...") matched against the alias table, applying that table's punctuation and suffix rules, so a name such as "Opus 5 (1M context)" with model id `claude-opus-5[1m]` resolves to `opus-5` rather than falling through as unrecognised. When no statement is present, assume Claude Fable 5.1 and record "executing model: none stated, assumed fable-5-1". When the name is not in the table, record "executing model unrecognised: <name>, treated as fable-5-1".
- Target model: the model the rearticulated prompt is written for. By default it equals the executing model, because the prompt is executed in-session. It differs only when the raw request is prompt authoring for an application, or when the user names a model or passes `--model`.

Resolution order for the target: (1) a `--model <alias>` flag anywhere in the raw request, stripped from the request text; (2) a model named in the raw request, only when the deliverable is for that model ("for claude-opus-5", "on Sonnet 5", "our Haiku bot", "system prompt for", "migrate to"); a model mentioned in passing ("fix the failing test; Opus 5 flagged it yesterday") does not switch the target; (3) the executing model. The Reading line always carries `Target model: <profile> (<how resolved>)`.

Division of labour: the content of the rearticulated prompt follows the target profile (sections 4 and 5 of the profile file); the skill's own narration, verification loop, delegation, and formatting follow the executing profile (section 6 of the profile file). The clearest case is verification: an authored prompt for Opus 5 carries no `<verification>` tag while Step 7 on a Fable 5.1 executing model still runs its checks; running on Opus 5 while authoring for Sonnet 5, the authored prompt keeps its tag and Step 7 reports the checks already performed instead of running a prescribed loop. [BP-232, BP-233, O5-42, O5-43, O5-56]

The skill never silently applies one model's snippet to another. When the target has no page, it applies the inline notes from the guide and the closest documented page, and marks that as an assumption (section 11). [BP-025]

## 5. Profile summaries

### fable-5-1 (Claude Fable 5.1, Claude Mythos 5.1)

Profile: `references/models/fable-5-1.md`. The default profile in this workspace. The page is organised by symptom; diagnose by what you observe and apply only the matching section's fix rather than adding every block at once (F51-05). Default additions on tool-using runs: progress_updates_line first and batch_nudge last (F51-36, F51-37, F51-43, F51-44); keep_changes_to_task on code changes (F51-117); targeted_edits (F51-136); formatting_in_chat_rule replacing inherited anti-formatting blocks (F51-73, F51-74); delivering_work for attended runs and operating_autonomously for unattended ones (F51-84 to F51-95); mannered_prose_short when prose runs dense (F51-69); search_name_as_written at low effort (F51-125, F51-126); long_output_budget_note as the last element of a long-deliverable prompt with the real max_tokens value (F51-141, F51-142); quoting_sources_example as a single example for summaries of retrieved sources (F51-76 to F51-78). Removals: "hold all findings for the final response", "keep progress text brief", anti-formatting language, compile-check phrasing (F51-35, BP-100, F51-73, F51-129). Trade-off to record: the operating_autonomously block lowers the model's tendency to ask about ambiguous requests, so Step 2 resolves ambiguity before it is grafted (F51-93); its opening sentence stays as written because it carries much of the effect (F51-91), and a sentence listing required confirmations follows it when Step 1 found external side effects (F51-92). Safeguards: finding vulnerabilities in source code is permitted; frame security reviews plainly; a blocked request returns `stop_reason: "refusal"`; the three false-positive triggers are compile-check phrasing, lesser-known languages without context, and tools that return base64 into context (F51-127 to F51-131).

Symptom to fix (the page's own index, F51-06 to F51-21):

| Symptom | Section and fix |
|---|---|
| Unsure which effort level, or latency and cost exceed the task | Consider all effort levels: start at high, sweep low, medium, xhigh, max; re-run the sweep from Fable 5 (F51-23, F51-25) |
| Little or no text between tool calls | Ask for user-facing progress updates: check thinking.display, remove suppression lines, add progress_updates_line (F51-32 to F51-37) |
| Agent loop issues one tool call per turn | Batch independent tool calls: batch_nudge as a turn-scoped system message (F51-43 to F51-52) |
| "bound to a different conversation", or the harness edits earlier turns | Keep the conversation history append-only (F51-53 to F51-64) |
| Prose runs long and dense | Writing density: mannered_prose_definition or mannered_prose_short (F51-67 to F51-70) |
| Chat replies carry less structure than the content needs | Formatting in chat: remove anti-formatting language or graft formatting_in_chat_rule (F51-73, F51-74) |
| Summaries reproduce source wording unmarked | Quoting retrieved sources: quoting_sources_example with the real tool name (F51-76 to F51-78) |
| Turn ends before the work is done, or asks permission for requested work | Finish the whole task: operating_autonomously and delivering_work (F51-80 to F51-102) |
| Client-side compaction drops constraints or exact details | Compaction summaries: compaction_summary_instruction (F51-103 to F51-113) |
| Unrequested fixes, or more test files than the task called for | Keep changes and tests to what the task asks for: keep_changes_to_task (F51-114 to F51-122) |
| Answers from memory instead of searching at low effort | Search triggering at low effort: search_name_as_written, or raise effort for the affected turns (F51-123 to F51-126) |
| Benign coding requests return `stop_reason: "refusal"` | Reduce safeguard false positives (F51-127 to F51-131) |
| Whole files rewritten for small changes | Prefer targeted edits: targeted_edits (F51-132 to F51-136) |
| Long deliverables at xhigh or max are slow or hit max_tokens | Leave room for long outputs: run at high, leave max_tokens headroom, long_output_budget_note (F51-137 to F51-142) |
| Lead agent idles while subagents run | Let the lead keep working: return immediately, deliver results later, separate wait tool (F51-143 to F51-148) |
| Answers about charts and dense images miss detail | Give vision work tools to crop and zoom (F51-149 to F51-152) |

### fable-5 (Claude Fable 5, Claude Mythos 5)

Profile: `references/models/fable-5.md`. Suited to problems too complex, long-running, or ambiguous for prior models; hand over the whole goal and let the model scope it rather than pre-decomposing (F5-04, F5-17, F5-67). Steer with one principle-level instruction instead of enumerated behaviours (F5-32, F5-35). Additions: f5_give_reason frame in `<context>` (F5-57); f5_lead_with_outcome or, for tool-heavy work, f5_readability_addendum in `<output_format>` (F5-34, F5-59); f5_scope_discipline on coding tasks at higher effort (F5-31); f5_state_boundaries under the assess posture (F5-40); f5_ground_progress wherever the model reports on tool work (F5-38); f5_act_when_ready on ambiguous requests (F5-24); f5_pause_only_when_needed paired with f5_autonomous_reminder for unattended pipelines (F5-36, F5-51, F5-52); f5_delegate_subagents for independent subtasks (F5-44); f5_self_verification_interval on long builds, as fresh-context verifier subagents rather than self-critique (F5-68, F5-69); f5_memory_notes only when no harness or project memory convention exists (F5-46); f5_ample_context only when a token count is visible to the model, never a quoted figure (F5-53 to F5-55). Removals: show-your-reasoning, think-aloud, and reflection lines, which trigger the reasoning_extraction refusal category (F5-71); thinking budgets and verbatim-thinking requests (F5-08); token counts (F5-54); long do-and-don't lists (F5-32). Executing behaviour: outcome-first final message, progress claims audited against tool results, delegate and keep working, ignore the harness's remaining-token count, and on a refusal say so plainly and name Opus 4.8 as the documented fallback rather than rephrasing (F5-10, F5-11, F5-20, F5-53).

### opus-5-5 (Claude Opus 5.5)

Profile: `references/models/opus-5-5.md`. Released 22 September 2026, baseline Opus 5, and an Opus 5 prompt is a reasonable starting point. Generates output more than 30 percent faster than Opus 5 and tends to finish the same task with fewer tokens. The page is organised by symptom, so diagnose by what you observe rather than grafting every block (O55-04). Additions: `o55_explore_multi_app` for agents working across several connected apps, because the information a task depends on often sits where the request does not point (O55-51); `o55_unattended_standing_instruction` for fully unattended pipelines, with `o55_continue_open_items` as the harness continuation message (O55-72 to O55-38); `o55_pasted_content_markup` with `o55_pasted_content_note` when users paste text into their messages, which is a prompt-injection guardrail rather than a guarantee (O55-63 to O55-66); `o55_time_matters` or an elapsed-against-budget line for multiagent harnesses (O55-54 to O55-57); `o55_answers_settled` for multi-turn chat where re-examining earlier answers adds latency (O55-60); `o55_answer_directly` at low effort when time to first token matters (O55-22); `o55_frontend_specific_avoids` for frontend work, naming patterns to avoid rather than asking for "not generic" (O55-72). Removals: `thinking: {"type": "disabled"}`, which this model does not accept; any instruction that stood in for thinking; any request for reasoning in the response text, which invites a reasoning_extraction decline; "think carefully before answering" lines in chat system prompts; carried-over Opus 5 effort values. Executing behaviour: writes progress updates between tool calls as thinking blocks, so a client rendering only text blocks looks silent; a text-only end of turn is a report rather than proof the task is done.

### opus-5 (Claude Opus 5)

Profile: `references/models/opus-5.md`. Built for complex agentic coding and long-horizon work; give the complete specification up front and let it run; it completes full tasks with no stubs (O5-04, O5-07, O5-08). Additions: explicit length, because effort does not shorten visible responses (O5-28): o5_conciseness for chat-style output (O5-31), o5_deliverable_length for files (O5-41), tone_preference closing a long prompt (O5-33); o5_progress_updates on tool-heavy tasks (O5-36); o5_scope_constraint for narrow tasks (O5-47); o5_correction_narration for user-facing output (O5-59); o5_delegation_guidance in authored prompts and SDK or custom-system-prompt runs, not in interactive Claude Code, whose claude_code preset already carries a delegation instruction (O5-51, O5-54); o5_thinking_disabled_mitigation only when an integration must keep thinking off (O5-67, O5-68). Removals: the `<verification>` tag and every verify, double-check, or re-verify line (O5-43, O5-57, BP-232, BP-233); conservative review filters, replaced by report-everything language with a later filtering pass (O5-12); do-not-think rules, which increase tag leakage (O5-66); stub allowances (O5-08); legacy vision workarounds (O5-20). Executing behaviour: narrate only on important findings and direction changes, Step 7 reports the checks already performed and runs no prescribed loop, delegate only large independent tracks (O5-36, O5-42, O5-56, O5-49).

### sonnet-5-5 (Claude Sonnet 5.5)

Profile: `references/models/sonnet-5-5.md`. Baseline Sonnet 5, and a Sonnet 5 prompt is a reasonable starting point; the page says an Opus model is the better choice for the hardest long-horizon work (S55-04). Initiative tracks effort: at low and medium it sometimes checks in before a coding task is done, and at xhigh and max it can start its own review rounds and launch reviewer subagents. Additions: `s55_carry_work_through` when the model stops short at low or medium effort, or its second paragraph alone (`s55_stop_when_done`) when the complaint is unrequested extras; `s55_no_self_review` at xhigh and max, which cut session cost by about a third in testing with no change in quality (S55-27); `s55_ideas_first` for open-ended requests where the user wanted options rather than a build; `s55_think_first` for reasoning tasks that return JSON, where the model often answers without thinking first; `s55_search_current_specifics` for chat and knowledge work, where it otherwise answers from training knowledge; `s55_real_verification` at low effort, where a change can be reported done without a check that exercises it. Removals: language discouraging tool use such as "only use tools when strictly necessary"; "hold all findings for the final response"; requests for reasoning in the response text; carried-over Sonnet 5 effort values; a harness token countdown after tool results in interactive sessions, which the model can misread as an injection. Executing behaviour: literal reading, verification that can thin out at low effort, and progress notes that come back as thinking blocks when they run beyond a sentence or two.

### sonnet-5 (Claude Sonnet 5)

Profile: `references/models/sonnet-5.md`. Literal and explicit, most of all at low and medium effort: it does not generalise an instruction from one item to another and does not infer unstated requests (S5-42, S5-20). Additions: explicit scope clauses on every instruction meant to generalise (s5_explicit_scope, S5-44, S5-45) and every wanted sub-step enumerated; s5_conciseness only when the user or the product fixes the verbosity (S5-07, S5-08); s5_warm_tone when a warmer voice is wanted (S5-48); s5_code_review_coverage with confidence and severity fields in the output schema, or s5_code_review_concrete_bar for single-pass filtering (S5-66, S5-69); frontend_aesthetics_short paired with a concrete AEFRM-shaped spec or s5_design_propose_directions, the sanctioned replacement for temperature-driven variety (S5-53 to S5-58); an explicit tool nudge when thinking is disabled and the task needs tools (S5-36); s5_low_effort_multistep only when the user has pinned low effort (S5-22); s5_thinking_trigger_guard only when latency is the stated concern (S5-29); context_compaction_persistence and spend_entire_context on long agentic work, because Sonnet 5 is one of the four models the guide names as context-aware (BP-241, BP-246, BP-261). Removals: temperature, top_p, top_k (400) and budget_tokens (400) (S5-49, S5-31); forced update cadence such as "After every 3 tool calls, summarize progress" (S5-40); conservative review filters (S5-64); requirements drip-fed over turns, gathered into one first-turn prompt instead (S5-61, S5-62). Executing behaviour: literal reading with stated assumptions, natural updates with no forced cadence, raise effort before prompting around shallow reasoning (S5-39, S5-21).

## 7. Effort is profile-local

An effort level is never carried from one profile to another. When the target changes, re-derive it from the new profile's section 2: Fable 5 to Fable 5.1 re-runs the sweep because level names do not correspond to the same amount of thinking (F51-25); Opus 4.8 to Opus 5 re-runs the sweep when defaults were carried over (O5-17); Sonnet 4.6 to Sonnet 5 maps one step down (4.6 high to 5 medium, 4.6 max to 5 high) and benchmarks by observed thinking length (S5-18, S5-19). Opus 5 to Opus 5.5 drops the default from high to medium, and Opus 5.5 at medium matches or exceeds Opus 5 at high on coding and knowledge work, so the sweep starts lower rather than being carried over (O55-20). Sonnet 5 to Sonnet 5.5 recalibrates the levels outright, so a level does not produce the same thinking as the same level on Sonnet 5 and a fresh sweep is the only safe move (S55-09). Effort is an API parameter, not a prompt instruction: the skill recommends a level in the Target model item and does not write "think harder" into the prompt (F5-25, S5-21, O48-20). Only levels the target's page names are recommended: Fable 5.1, Sonnet 5, and Opus 4.8 name max; Fable 5 and Opus 5 name low, medium, high, xhigh only.

## 10. How to switch rows

Prompt authoring for another model. When the raw request is "write a system prompt for", an API call, SDK code, an agent loop, a harness, or names a model with "for", "on", "our X bot", or "migrate to", the target switches to that model's profile and the taxonomy row "prompt authoring for another model" applies. Open `references/models/<target>.md`, apply its section 4 (add) and section 5 (remove or convert) to the authored prompt, and state in the Target model item: profile and how resolved; recommended effort with the page section; thinking configuration in the page's exact syntax (`thinking: {type: "adaptive"}` on 4.6 to 4.8, omitted or `{type: "disabled"}` on Sonnet 5 and Opus 5 with the high-effort cap on Opus 5, nothing on the Fable family where thinking is always on); max_tokens headroom, the 64k note on Opus 4.8 at xhigh or max, or the 30 percent tokenizer note on Sonnet 5; parameters removed with the 400 reason; environment caps named as controls the prompt cannot set. The authored prompt's content follows the target; the skill's own Steps 6 and 7 follow the executing model (section 4 of this file). On this row the recommended effort, the thinking configuration, and the max_tokens notes all describe the authored deliverable's own runtime, not this turn's: the executing turn's effort is a harness setting and is never recommended inside the prompt.

A named model in an ordinary request. "Fix the flaky test that Sonnet 5 wrote yesterday" names a model in passing: the target stays the executing model and no row switches. "Rewrite this prompt for Sonnet 5" or `--model sonnet-5` switches. When a pasted prompt was written for an older model (budget_tokens, prefill, anti-laziness amplifiers, anti-formatting blocks), the migration checklist in SKILL.md Step 4 runs against the target's section 5 (BP-005).

Moving between two paged models. Keep the substance of the source prompt and apply only the target page's deltas: Fable 5 to Fable 5.1 (F51-04), Opus 4.8 to Opus 5 (O5-05), Sonnet 4.6 to Sonnet 5 (S5-04), Opus 4.7 to Opus 4.8 (O48-04). Re-derive effort (section 7). Record every removal and substitution in the Changed line.

Executing model other than Fable 5.1. When the identity statement resolves to another profile, open that profile and follow its section 6 in Steps 5 to 7: on Opus 5 narrate on findings only, report checks performed, skip o5_delegation_guidance in interactive Claude Code; on Fable 5 lead with the outcome, audit progress against tool results, ignore the token count; on Sonnet 5 and Opus 4.8 read literally, state assumptions, give natural updates.
